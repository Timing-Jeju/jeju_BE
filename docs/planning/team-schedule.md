## 3. 주차별 상세 일정

### 1주차: 구조 고정과 병렬 작업 준비

| 역할 | 작업 | 완료 기준 |
|---|---|---|
| 백엔드 1 | 현재 fixture 3종 정리, 수집 스크립트 안정화, DB 테이블 초안 작성 | 장소/정류장/버스 예시 데이터 검증 통과 |
| 백엔드 2 | API DTO/schema 정의, trip plan 응답 구조 설계, 계산 엔진 인터페이스 작성 | 프론트가 사용할 `POST /api/trips/plan` 응답 예시 확정 |
| 프론트엔드 1 | 앱 프로젝트 골격, 라우팅, API client, mock response 연결 | fixture/mock 기반 첫 화면 렌더링 |
| 디자이너 1 | 핵심 사용자 흐름 정의: 입력 → 분석 → 위험 → 복구 | 1개 대표 시나리오 user flow 완성 |
| 디자이너 2 | 화면 톤앤매너, 카드/상태 색상, 발표용 화면 구조 | 기본 UI 스타일 가이드 완성 |

### 2주차: 데이터 연동과 화면 뼈대

| 역할 | 작업 | 완료 기준 |
|---|---|---|
| 백엔드 1 | TourAPI 장소 매칭, TAGO 정류장 매칭, seed/import 구조 구현 | 제주공항/성산일출봉/섭지코지 API 데이터 재수집 가능 |

### 3주차: 일정 계산 MVP

| 역할 | 작업 | 완료 기준 |
|---|---|---|
| 백엔드 1 | 버스 노선/시간표 확장 조사, 데이터 상태 API 구현 | import 기준일과 데이터 상태를 API로 제공 |
| 백엔드 2 | TransitEngine, RiskEngine, leave-by 계산 구현 | 후보 버스, 대기시간, 놓쳤을 때 위험도 계산 |

## 5. 작업 의존성

1. 디자이너는 1주차에 전체 UX를 먼저 닫아야 프론트가 화면 구조를 갈아엎지 않는다.
2. 백엔드 2는 1주차에 API 응답 DTO를 먼저 고정해야 프론트가 mock으로 병렬 개발할 수 있다.
3. 백엔드 1의 데이터 수집은 2주차까지 최소 corridor 기준으로 안정화되어야 3주차 계산 엔진이 막히지 않는다.
4. OpenAI는 4주차에 붙이는 것이 좋다. 1~3주차에는 서버 계산 결과를 먼저 신뢰 가능하게 만들어야 한다.
5. 발표 안정성을 위해 5주차에는 live API만 믿지 말고 seed/demo mode를 반드시 둔다.
