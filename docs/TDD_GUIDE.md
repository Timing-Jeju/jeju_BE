# TDD 가이드

## Red

Issue의 Acceptance Criteria를 성공, 실패, 경계값 테스트로 바꿉니다. 운영 코드를 작성하기 전에 테스트를 실행해 의도한 이유로 실패하는지 확인하고 명령, 테스트명, 핵심 실패 원인을 기록합니다. Red 상태 자체를 원격에 실패 커밋으로 보낼 필요는 없습니다.

## Green

실패 테스트를 통과시키는 최소 코드만 작성합니다. 관련 테스트와 전체 테스트를 다시 실행하고 결과를 기록합니다. 테스트에서 운영 외부 서비스에 접근하지 않으며 시간, UUID, 랜덤값은 제어 가능한 의존성으로 만듭니다.

## Refactor

중복 제거, 이름 개선, 책임 분리, 트랜잭션과 도메인 경계를 점검한 뒤 전체 테스트를 재실행합니다. feat/fix/refactor 브랜치에서 운영 코드가 바뀌면 대응 테스트 변경이 필요합니다. 예외가 필요하면 Issue와 PR에 구체적 근거를 적고 Reviewer 승인을 받습니다.

## 테스트 분류

JUnit `@Tag`로 `unit`, `slice`, `integration`, `architecture`를 구분합니다. 한 테스트는 한 행동을 검증하며, 메서드 이름에서 조건과 기대 결과가 드러나야 합니다. 정상 흐름뿐 아니라 Validation, 권한, 예외, 오류 응답, 동시성과 경계값을 다룹니다.

JaCoCo 최소값은 `services/spring-api/build.gradle`의 `minimumCoverage` 한 곳에서 관리합니다. 초기 골격은 비즈니스 코드가 없어 0%에서 시작하며, 첫 핵심 도메인 Issue에서 의미 있는 기준으로 올려야 합니다.
