## 2026-05-19 App Engineering Review: 3-Role Technical Plan

요청: **프론트엔드 개발자, 백엔드 개발자, AI 개발자 3개 역할로 나눠 앱으로 구현할 기술을 정하고 리뷰한다.**

결론: **Expo 모바일 앱 + Spring Boot API + OpenAI Responses API 조합으로 간다.** 기존 PWA 계획은 본선 데모용으로도 가능했지만, "앱"으로 만들겠다면 Expo가 맞다. 네이티브 iOS/Android를 각각 만들면 공모전 MVP에는 너무 무겁다.

### Role Split

| Role | Owns | Does not own | Main success metric |
|---|---|---|---|
| Frontend App Developer | Expo app, mobile UI, live timeline, recovery UX, demo flow | 교통 계산, AI 사실 생성, 데이터 import | 심사위원 앞에서 3분 데모가 끊기지 않는다. |
| Backend Developer | REST API, TourAPI/버스 데이터, timetable/risk/recovery engine, DB/cache | UI state, LLM prompt wording | 제출본의 100/38/81 점수와 +42~48분 위험을 재현한다. |
| AI Developer | OpenAI structured parsing, explanation, recovery copy, hallucination guard, evals | 버스 번호/시간 생성, 경로 가능성 판단 | AI가 계산된 사실만 설명하고 JSON contract를 깨지 않는다. |

#### AI Developer

| Layer | Choice | Rationale |
|---|---|---|
| API | OpenAI Responses API | structured JSON output과 text generation을 한 API로 관리한다. |
| SDK | Official OpenAI Java SDK | API key를 서버에만 두고 Spring service에서 호출한다. |
| Default model | env var `OPENAI_MODEL`, default to current mini reasoning/text model | 모델명은 바뀐다. 코드에 `gpt-5.4-mini` 같은 값을 박지 않는다. |
| Output contract | Structured Outputs JSON Schema | 자연어 입력을 서버 타입으로 검증한다. |
| Guardrail | deterministic facts only | AI는 설명자다. TransitEngine이 사실을 소유한다. |
| Fallback | deterministic Korean templates | OpenAI timeout에도 앱은 결과를 보여준다. |
| Evals | golden prompt fixtures + schema violation tests | "버스 시간을 지어내지 않는다"를 테스트한다. |

AI call boundaries:

```text
Allowed:
  - parse user trip text into structured fields
  - ask clarification when date/time/place is missing
  - explain computed risk in plain Korean
  - summarize recovery options already generated by backend

Forbidden:
  - invent route numbers
  - invent departure/arrival times
  - decide if a bus route exists
  - hide low confidence or stale timetable data
```

### Architecture Review

Severity: **GO with 3 guardrails.**

```text
Expo App
  |
  | REST JSON
  v
Spring Boot API
  |
  +-- trip/ TripPlannerService
  |     |
  |     +-- ai/AiIntentParser
  |     +-- place/TourPlaceMatcher
  |     +-- transit/StopMatcher
  |     +-- transit/TimetableEngine
  |     +-- risk/RiskEngine
  |     +-- risk/RecoveryEngine
  |     +-- ai/AiExplanationService
  |
  +-- rto/CorridorInsightService
  +-- debug/DataHealthController
  |
  v
PostgreSQL + PostGIS
  |
  +-- tour_places
  +-- bus_stops
  +-- bus_routes
  +-- timetable_entries
  +-- trip_plans
  +-- risk_events

External:
  TourAPI, Jeju public bus data, OpenAI API
```

Architecture findings:

1. **[P1] Native map SDK is a scope trap.** Kakao/Naver native SDK integration can consume more time than the actual product. Use deep links and optional WebView preview for MVP. Native map SDK is Phase 2.
2. **[P1] Full 제주 route planner is not the MVP.** Use a deterministic east-corridor graph first. Full route-stop sequence validation is Phase 2.
3. **[P1] AI must be behind the backend.** API keys, prompts, and schema validation stay server-side. The app never calls OpenAI directly.

Architecture decisions:

| Decision | Status | Why |
|---|---|---|
| Expo app instead of PWA | Accepted | User wants an app. Expo is the smallest serious app path. |
| Spring Boot API remains | Accepted | Existing plan already fits Spring, data import, PostGIS, API boundaries. |
| PostGIS remains but fixture mode is mandatory | Accepted | Spatial search is core, but demo cannot depend on live import success. |
| Native map SDK deferred | Accepted | It does not prove the core product and increases build risk. |

### Code Quality Review

No source code exists yet, so this is a plan-level code quality review.

Required quality boundaries:

| Boundary | Rule |
|---|---|
| Frontend | Components do not calculate risk. They render API results and local UI state only. |
| Backend | `RiskEngine` is pure and deterministic. No OpenAI call inside scoring. |
| AI | AI services accept computed facts and return structured explanation only. |
| Data | Fixtures and imported data share the same read model. No separate demo-only calculation path. |
| Errors | Every external API failure returns a typed application error with user-safe copy. |

Code quality findings:

1. **[P1] Do not fork demo logic from production logic.** Fixture mode must feed the same `TimetableEngine`, `RiskEngine`, and `RecoveryEngine`. Otherwise the demo can pass while the app is fake.
2. **[P2] Keep role modules separate.** `ai/`, `transit/`, `risk/`, `place/`, `trip/` boundaries prevent "one giant TripService" from becoming the whole backend.
3. **[P2] Store data confidence as data, not prose.** Use fields like `source`, `dataVersion`, `confidence`, `stale`, `fallbackUsed`; do not bury that in AI text.

### Performance Review

Performance targets:

| Path | Target | Rule |
|---|---:|---|
| App first usable screen | < 2s after bundle load | Ship fixture/demo data with the app. |
| Plan generation, warm cache | < 5s | TourAPI cache and corridor fixture must be warm. |
| Live state update | < 300ms | No OpenAI call, no external API call. |
| Recovery generation | < 1s deterministic, < 3s with AI explanation | Generate options first, then AI summarizes. |
| RTO dashboard | < 1s | Use precomputed corridor aggregates for demo. |

Performance findings:

1. **[P1] Never call OpenAI in live countdown.** Live state is deterministic math only.
2. **[P2] TourAPI images can be lazy.** Image failure must not block planning.
3. **[P2] Precompute demo corridor.** The final demo should not import XLSX on the fly.

Parallel lanes:

```text
Lane A: Backend API + engines -> API integration tests
Lane B: Mobile app shell + fixture-mode UI -> E2E demo script
Lane C: AI schemas + eval fixtures -> schema/eval tests
Lane D: Demo docs/runbook -> QA checklist
```

Execution order:

```text
1. Define shared API DTOs and fixture schema first.
2. Launch Lane A + Lane B + Lane C in parallel.
3. Merge APIs and app screens.
4. Run final E2E demo and fill Lane D with exact commands.
```

Conflict flags:

- Lane A and Lane C both touch backend `ai/` DTOs. Agree JSON schemas before splitting work.
- Lane A and Lane B both depend on API response shape. Freeze OpenAPI/DTO contract early.

## Verdict

**GO, with bounded MVP scope.**

타이밍제주는 실제 구현 가능하다. 단, 첫 버전의 성공 기준을 "제주 전역 모든 버스 경로를 완전 탐색"으로 잡으면 위험하다. 확인된 공개 데이터만 보면 정류소, 노선 기본 정보, 시간표, TourAPI 관광정보는 충분하지만, 임의 출발지-목적지 간 버스 경로 탐색에 필요한 **노선별 정류장 순서와 환승 그래프 품질**은 별도 검증이 필요하다.

따라서 MVP는 이렇게 잠근다.

> 제주 동쪽 대표 관광 코리도어를 대상으로, TourAPI 장소 매칭 + 정류장 매칭 + 시간표 기반 위험도 계산 + OpenAI 설명/복구안을 구현한다.

MVP 구현 가능성 점수: **8/10**

감점 이유:

- 제주 버스 시간표가 XLSX/기관 사이트 다운로드 중심이라 import 작업이 필요하다.
- 정류장/노선 기본 정보만으로는 전역 환승 라우터를 만들기 어렵다.
- 실시간 도착 정보는 초기 scope에서 제외해야 안정적이다.

| File import | Apache POI | 제주 버스 시간표 XLSX import에 필요하다. |
| Spatial query | PostGIS `ST_DWithin`, `ST_Distance` | 관광지 주변 정류장 탐색의 핵심이다. |
| Seed strategy | Demo corridor seed + imported public data | 전역 라우터 전에는 검증된 대표 코스를 먼저 완성한다. |

### OpenAI

OpenAI API는 필수 scope다.

| Layer | Choice | Reason |
|---|---|---|
| API | OpenAI Responses API | 신규 앱에서 text/structured output/tool flow를 한 API로 관리하기 좋다. |
| SDK | Official `openai-java` or Spring Boot starter | Spring 서버에서 API key를 안전하게 보관하고 호출한다. |
| Default model | `gpt-5.4-mini` | 일정 파싱/설명/복구안에는 비용과 지연이 더 중요하다. |
| Premium/admin model | `gpt-5.5` optional | 발표용 고품질 설명 생성, 관리자 분석 요약에만 쓴다. |
| Output mode | Structured Outputs with JSON Schema | 장소 후보, 사용자 선호, 복구안 같은 결과를 서버 타입으로 검증한다. |

OpenAI의 역할:

- 자연어 일정 입력을 구조화한다.
- 사용자의 선호와 우선순위를 추출한다.
- 서버가 계산한 위험도와 대체안을 쉬운 한국어로 설명한다.
- 버스를 놓쳤을 때 선택지를 요약한다.
- 외국인 모드에서는 탑승 안내 문장을 번역/간소화한다.

OpenAI가 하면 안 되는 일:

- 버스 번호를 지어내기.
- 출발 시각을 직접 생성하기.
- 경로 가능 여부를 판단하기.
- TourAPI에 없는 관광지 정보를 사실처럼 말하기.

Rule:

> TransitEngine owns facts. OpenAI explains facts.

## Feasibility Risks

### P1: Full bus routing data may be incomplete

Confirmed public data includes stop basics, route basics, and timetable files. That is not always enough to compute arbitrary transit routes. The missing piece is reliable route-stop sequence and timetable-to-stop alignment.

Decision:

- MVP uses a controlled corridor graph for east Jeju.
- Engineering task 1 is to verify route-stop sequence availability from JejuDataHub technical docs or national bus route-stop APIs.
- If route-stop sequence is not reliable, do not promise full Jeju routing.

### P1: OpenAI hallucination can destroy trust

If AI invents "201번 11:55 탑승" and it is wrong, the product fails.

Decision:

- All times/routes come from server-calculated `TripLeg`.
- OpenAI receives only computed facts and must output explanation JSON.
- UI labels every AI explanation with source confidence.
- Template fallback exists when OpenAI fails.

### P2: TourAPI traffic limit

TourAPI developer traffic can be tight for repeated testing.

Decision:

- Cache all TourAPI responses by contentId/search key.
- Warm cache for demo places.
- Do not fetch images repeatedly.
- Use source timestamp and cache age in admin health.

### P2: Time zone/date/day-type bugs

Bus timetable depends on date, weekday/weekend/holiday, and late-night routes.

Decision:

- Store all local travel times as `Asia/Seoul`.
- Add day-type field to timetable entries.
- MVP demo date should be fixed and tested.

## Performance

Targets:

- Initial plan generation: under 5s with warm TourAPI cache.
- Live timeline update: under 300ms, no OpenAI call.
- Recovery generation: under 3s if OpenAI succeeds, under 500ms template fallback.
- TourAPI cache hit rate for demo: 90%+.

Performance rule:

> Never call OpenAI on every countdown tick. OpenAI is for parse/explain/recover, not live state.

## Security

- `OPENAI_API_KEY` only on Spring server, never frontend.
- TourAPI and map API keys separated by client/server use.
- No account required for MVP.
- Anonymous trip session IDs.
- Precise location not persisted by default.
- Rate limit OpenAI-backed endpoints.
- Log prompt metadata, not full sensitive user location history.
