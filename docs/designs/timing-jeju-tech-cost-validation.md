## Validation Assumptions

- MVP area: 제주공항, 함덕, 월정리, 성산일출봉, 섭지코지, 성산/서귀포 숙소 placeholder.
- Users do not need accounts for MVP.
- Map SDK: Kakao Maps Web API first.
- Backend: Spring Boot 4, Java 21.
- Frontend: React Router Framework Mode, Vite, TypeScript.
- Database: PostgreSQL + PostGIS.
- OpenAI model: `gpt-5.4-mini` by default, `gpt-5.5` only for optional high-quality/admin summaries.
- Realtime bus arrival is Phase 2, not an MVP dependency.
- Currency conversion is planning-only: `1 USD = 1,400 KRW`.

## Critical Architecture Rule

```text
TransitEngine owns facts.
OpenAI explains facts.
```

OpenAI must not invent:

- bus number
- departure time
- arrival time
- route feasibility
- TourAPI place facts

OpenAI may generate:

- structured parse of natural language trip input
- user preference extraction
- explanation of risk based on computed facts
- missed-bus recovery summary
- multilingual wording for already-computed guidance

## Validation Flow

```text
User input
  |
  v
OpenAI structured parse
  |-- invalid JSON -> retry once -> template/manual fallback
  v
TourAPI place match
  |-- ambiguous -> user chooses candidate
  |-- no match -> manual place entry
  v
PostGIS nearest stop
  |-- no stop nearby -> high-risk leg
  v
Corridor TransitEngine
  |-- no timetable candidate -> no-route recovery
  v
RiskEngine
  |-- deterministic score, leave-by time, waiting risk
  v
OpenAI explanation
  |-- timeout -> deterministic Korean template
  v
React timeline/cards/map
```

## Proof-of-Feasibility Tasks

These should be completed before visual polish.

1. TourAPI place match POC
   - Input: `함덕해수욕장`, `월정리해변`, `성산일출봉`
   - Output: content ID, title, address, latitude, longitude, image URL if available
   - Pass condition: 3/3 match or candidate list shown

2. Jeju stop import POC
   - Import stop ID, name, latitude, longitude into PostGIS
   - Query nearest stop within 800m of each TourAPI place
   - Pass condition: each MVP place has at least one plausible stop candidate

3. Timetable import POC
   - Download route timetable XLSX for MVP corridor routes
   - Parse into `route_id`, `stop_id or stop_name`, `service_day`, `departure_time`
   - Pass condition: at least one airport-to-east itinerary can produce leave-by times

4. Corridor routing POC
   - Hard-code verified route-stop sequence for MVP corridor only
   - Compute next available bus after `current_time + walk_time + buffer`
   - Pass condition: returns bus candidate, wait time, and missed-bus penalty

5. OpenAI structured output POC
   - Use `gpt-5.4-mini`
   - Schema: places, arrival_time, preferences, must_visit, pace
   - Pass condition: 20 Korean travel prompts parse to valid schema with no invented bus facts

6. End-to-end go/no-go
   - Input: `10시에 제주공항 도착, 함덕, 월정리, 성산일출봉 가고 싶어`
   - Output:
     1. matched TourAPI places
     2. nearest stops
     3. route/timetable candidates
     4. risk score
     5. leave-by time
     6. missed-bus recovery
     7. OpenAI explanation citing computed facts only

If this end-to-end path works, the project is real. If it fails, UI work should pause.

## OpenAI Cost Model

Current official model guidance supports `gpt-5.4-mini` for lower-latency, lower-cost workloads and `gpt-5.5` for complex reasoning.

Pricing basis used:

| Model | Input | Output |
|---|---:|---:|
| `gpt-5.4-mini` | $0.75 / 1M input tokens | $4.50 / 1M output tokens |
| `gpt-5.5` | $5.00 / 1M input tokens | $30.00 / 1M output tokens |

Per itinerary generation assumption:

| Call | Input tokens | Output tokens | Frequency |
|---|---:|---:|---:|
| Natural language parse | 1,200 | 400 | 100% |
| Risk explanation | 1,800 | 700 | 100% |
| Missed-bus recovery | 1,500 | 600 | 20% |

Weighted tokens per itinerary:

```text
Input  = 1,200 + 1,800 + (1,500 * 0.2) = 3,300 tokens
Output =   400 +   700 + (  600 * 0.2) = 1,220 tokens
```

Estimated `gpt-5.4-mini` cost:

```text
Input cost  = 0.0033M * $0.75 = $0.002475
Output cost = 0.00122M * $4.50 = $0.00549
Total       = $0.007965 per itinerary
```

Rounded planning number: **$0.008 per AI itinerary**.

| Monthly AI itineraries | `gpt-5.4-mini` estimate | KRW estimate |
|---:|---:|---:|
| 500 | $4 | 5,600원 |
| 1,000 | $8 | 11,200원 |
| 5,000 | $40 | 56,000원 |
| 10,000 | $80 | 112,000원 |
| 50,000 | $398 | 557,000원 |

If `gpt-5.5` is used for every itinerary, cost rises about 6.7x:

```text
Input cost  = 0.0033M * $5.00  = $0.0165
Output cost = 0.00122M * $30.00 = $0.0366
Total       = $0.0531 per itinerary
```

Decision:

- Use `gpt-5.4-mini` for user-facing parse/explain/recover.
- Use `gpt-5.5` only for admin summaries, proposal copy, or premium offline analysis.
- Never call OpenAI on every live countdown tick.

## Performance Review

Expected bottlenecks:

| Path | Risk | Fix |
|---|---|---|
| TourAPI keyword matching | quota and latency | cache by keyword/content ID |
| nearest stop search | slow without index | PostGIS geography/geometry index |
| timetable lookup | slow if XLSX parsed live | import to DB, never parse XLSX per request |
| OpenAI explanation | 1-3s latency | async loading state + template fallback |
| live countdown | excessive API calls | compute client-side from server facts |

Performance target:

| Operation | Target |
|---|---:|
| Existing plan live update | <300ms, no OpenAI |
| Create itinerary with cached TourAPI | <3s |
| Create itinerary with OpenAI + uncached TourAPI | <6s |
| Missed-bus recovery | <3s with OpenAI, <500ms fallback |

## Failure Modes

| Failure | User Impact | Handling |
|---|---|---|
| OpenAI timeout | Explanation delayed | deterministic template fallback |
| OpenAI invalid JSON | Parser fails | retry once, then manual candidate flow |
| TourAPI quota reached | Place search degraded | cached places and demo seed |
| Timetable missing route | no bus option | show high-risk/no-route recovery |
| Stop API missing lat/lng | nearest stop wrong | validation rejects invalid rows |
| DB unavailable | app unusable | health endpoint, restore from seed |
| Map SDK quota issue | map blank | list/timeline still works without map |

Critical gap:

- Full Jeju route-stop sequence remains unverified.
- This is acceptable only if the MVP explicitly limits routing to a verified corridor graph.

## NOT In Scope

- 제주 전역 arbitrary transit routing before route-stop sequence validation.
- Real-time bus arrival as a hard dependency.
- Native iOS/Android.
- Paid notifications.
- User accounts and social login.
- Group trip sharing.
- Payment, booking, reservations.
- Weather-based optimization beyond simple tagged fallback.
