OpenAI는 필수로 사용하지만, 버스 번호·시간·가능 경로는 생성하지 않는다. 서버가 계산한 사실을 구조화하고 설명하는 역할만 한다.

**타이밍제주**

### 부제

**버스 시간을 놓치지 않는 제주 뚜벅이 AI 여행 일정 매니저**

### 한 문장 소개

타이밍제주는 제주 뚜벅이 여행자가 입력한 여행 일정을 TourAPI 관광정보와 제주 버스 정류소·노선·시간표 데이터로 검증하고, OpenAI API를 통해 일정 위험과 복구안을 이해하기 쉽게 설명하는 AI 일정 운영 서비스다.

### 한 줄 차별화

관광지를 추천하는 앱이 아니라, **버스 시간 때문에 여행 일정이 무너지지 않도록 운영하는 앱**이다.

## 2. 문제 정의

제주도는 관광지가 넓게 퍼져 있고, 렌터카 없이 이동하는 여행자는 버스 배차 간격, 정류장 위치, 환승, 도보 이동 시간 때문에 일정 실패를 겪기 쉽다.

사용자는 지도 앱으로 A에서 B까지 길찾기는 할 수 있지만 다음 질문을 하루 일정 전체 기준으로 판단하기 어렵다.

- 지금 관광지에서 더 머물러도 되는가?
- 몇 시까지 나가야 다음 버스를 안정적으로 탈 수 있는가?
- 버스를 놓치면 다음 일정이 얼마나 밀리는가?
- 일정이 밀리면 어떤 장소를 줄이거나 대체해야 하는가?
- 다음 버스까지 시간이 떠도, 실제로 다녀올 수 있는 주변 장소는 어디인가?

타이밍제주의 목표는 "가볼 만한 곳" 추천이 아니라 **실행 가능한 하루 일정 운영**이다.

## 3. 공모전 적합성

2026 관광데이터 활용 공모전은 한국관광공사 OpenAPI를 활용한 신규 웹·앱 관광서비스를 대상으로 한다. 타이밍제주는 TourAPI를 부가 정보가 아니라 핵심 데이터로 사용한다.

TourAPI 사용 지점:

- 자연어 장소명을 TourAPI 관광지 후보로 매칭.
- 제주 지역 관광지 좌표, 주소, 카테고리, 이미지 조회.
- 현재 위치 기반 주변 관광지/음식점/문화시설 후보 조회.
- 남는 시간 안에 가능한 주변 관광지 추천.
- 추천 카드에 TourAPI 이미지와 기본 소개 표시.

공모전 차별점:

- TourAPI 관광정보를 제주 버스 실행 가능성과 결합한다.
- 단순 추천이 아니라 일정 실패 위험을 줄이는 서비스다.
- 제주 지역 특화 문제가 명확하다.

## 5. MVP 기능 범위

### 5.1 자연어 일정 입력, 구현 가능

사용자는 자연어로 일정을 입력한다.

OpenAI API는 다음 구조의 JSON으로만 응답한다.

```json
{
  "arrivalTime": "10:00",
  "places": ["제주공항", "함덕", "월정리", "성산일출봉"],
  "preferences": ["뚜벅이", "대기시간 최소화"],
  "mustVisit": ["성산일출봉"],
  "pace": "normal"
}
```

구현 방식:

- OpenAI Responses API 사용.
- Structured Outputs JSON Schema 사용.
- JSON schema validation 실패 시 1회 retry.
- 재실패 시 직접 입력 UI로 fallback.

정확도 제어:

- OpenAI가 버스 시간이나 버스 번호를 반환하지 못하도록 schema에서 제외한다.
- 장소 후보는 TourAPI 매칭 결과로 다시 검증한다.

### 5.2 TourAPI 장소 매칭, 구현 가능

사용자가 입력한 장소명을 TourAPI 키워드검색으로 조회한다.

사용 데이터:

- 관광지명
- contentId
- contentTypeId
- 주소
- mapX, mapY
- 이미지 URL
- 카테고리
- 기본 소개

정확도 정책:

| 상황 | 처리 |
|---|---|
| 정확히 1개 후보 | 자동 매칭 |
| 비슷한 후보 여러 개 | 후보 선택 UI 표시 |
| 후보 없음 | 직접 장소 입력 또는 추천 장소 선택 |
| 좌표 없음 | 일정 계산 대상에서 제외 |

### 5.3 정류장 자동 매칭, 구현 가능

TourAPI 장소 좌표와 제주 버스 정류소 기본 정보의 경위도를 비교해 주변 정류장을 찾는다.

구현 방식:

- PostgreSQL + PostGIS 사용.
- 반경 800m 내 정류장 후보 조회.
- 가장 가까운 정류장 3개를 후보로 저장.
- 노선 방향 정보가 있으면 우선순위 보정.

정확도 정책:

| 거리 | 신뢰도 | UI 표현 |
|---:|---|---|
| 0-250m | 높음 | 자동 선택 가능 |
| 251-800m | 중간 | 사용자 확인 권장 |
| 800m 초과 | 낮음 | "가까운 정류장 없음" 표시 |

주의:

- 정류장이 가까워도 도로 방향, 횡단보도, 실제 승차 위치가 다를 수 있다.
- MVP에서는 "정류장 후보"로 표현하고, 절대적 안내처럼 말하지 않는다.

### 5.4 시간표 기반 버스 타이밍 매니저, 구현 가능

각 일정 구간마다 leave-by 시각과 위험도를 계산한다.

계산식:

```text
readyAt = 현재시각 + 체류시간 + 정류장까지 도보시간 + 안전버퍼
nextBus = readyAt 이후 첫 시간표 후보
waitMin = nextBus.departure - readyAt
missedPenalty = nextBusAfterNext.departure - nextBus.departure
```

UI 예시:

```text
함덕해수욕장 -> 월정리해변
나가야 하는 시각: 12:10
정류장까지 도보: 약 1분
안전 버퍼: 5분
후보 버스: 12:37
예상 대기: 21분
놓치면 추가 대기 위험: 약 42분
상태: 위험
```

정확도 정책:

- 시간표 기반 예측임을 명시한다.
- 실시간 지연/결행은 MVP에서 보장하지 않는다.
- 데이터 상태 화면에 시간표 import 기준일을 표시한다.

### 5.5 라이브 타임라인, 구현 가능

여행 중 현재 시각을 기준으로 상태를 업데이트한다.

상태:

- 초록: 여유.
- 노랑: 출발 준비.
- 빨강: 일정 위험.

구현 방식:

- 서버가 계산한 leave-by, nextBus, missedPenalty를 프론트에 전달.
- 프론트는 현재 시각으로 countdown만 갱신.
- countdown tick마다 OpenAI를 호출하지 않는다.

### 5.6 버스를 놓쳤을 때 주변 추천, 구현 가능

버스를 놓쳐 다음 버스까지 시간이 생기면, TourAPI 위치기반 관광정보를 사용해 주변 후보를 조회한다.

추천 조건:

```text
사용 가능 시간 = 다음 버스 출발시각 - 현재시각 - 정류장 복귀 버퍼
후보 총 소요시간 = 왕복 이동시간 + 예상 체류시간
후보 총 소요시간 <= 사용 가능 시간
```

추천 대상:

- 짧은 포토스팟.
- 카페/음식점.
- 해변 산책.
- 기념품/시장.
- 실내 관광지.

예상 체류 시간은 MVP에서 규칙 기반으로 둔다.

| 후보 유형 | 기본 체류시간 |
|---|---:|
| 포토스팟 | 15-20분 |
| 카페 | 25-40분 |
| 해변 산책 | 20-40분 |
| 소규모 관광지 | 40-60분 |
| 전시/박물관 | 60분 이상 |

정확도 정책:

- 추천은 "가능 후보"이지 "반드시 만족스러운 장소"가 아니다.
- 영업시간, 휴무, 혼잡도는 MVP에서 보장하지 않는다.
- TourAPI 데이터와 지도 링크를 함께 제공해 사용자가 최종 확인할 수 있게 한다.

### 5.7 관광지 체류 지연 시 일정 재계산, 구현 가능

사용자가 관광지에 오래 머물러 일정이 밀리면 서버가 이후 구간을 다시 계산한다.

구현 가능한 범위:

- 현재 위치/현재 시각 기준 이후 구간 재계산.
- 다음 버스 후보 재선택.
- 필수 일정 유지.
- 선택 일정 삭제.
- 체류시간 단축안 제시.
- 주변 추천으로 대기시간 보완.

OpenAI 역할:

- 서버가 만든 복구안을 자연어로 설명.
- 사용자의 mustVisit 정보를 반영해 선택지를 정리.

OpenAI가 하지 않는 일:

- 버스 시간 생성.
- 모르는 관광지 임의 추가.
- 제주 전역 최적 경로 탐색.

복구안 예시:

```text
월정리 체류가 35분 길어져 성산일출봉 도착이 늦어질 수 있습니다.
성산일출봉은 필수 일정으로 유지하고, 월정리 체류를 지금 종료하는 것을 추천합니다.
대안으로 다음 버스까지 42분이 남으면 근처 카페 1곳을 추천할 수 있습니다.
```

### 5.8 데이터 상태 화면, 구현 가능

심사와 데모에서 신뢰를 주기 위해 관리자/데모용 데이터 상태 화면을 제공한다.

표시 항목:

- TourAPI 마지막 성공 호출 시각.
- 버스 정류소 데이터 import 시각.
- 버스 노선 데이터 import 시각.
- 시간표 import 기준일.
- OpenAI fallback 발생 횟수.
- seed data 사용 여부.

이 기능은 작지만 중요하다. 공모전 심사에서 "데이터 기반 서비스"라는 신뢰를 높인다.

## 7. API 검증표

### 7.1 TourAPI 국문 관광정보

| 항목 | 확인 내용 |
|---|---|
| 제공기관 | 한국관광공사 |
| API 유형 | REST |
| 데이터 포맷 | JSON+XML |
| 비용 | 무료 |
| 트래픽 | 개발계정 1,000, 운영계정은 활용사례 등록 시 증가 가능 |
| 제공 기능 | 지역기반, 위치기반, 키워드검색, 행사정보, 숙박정보, 공통정보, 소개정보, 이미지정보 등 |
| MVP 사용 | 장소 매칭, 주변 추천, 이미지/소개 표시 |

## 13. 핵심 API 설계

```text
POST /api/trips/parse
  자연어 입력을 구조화한다.

POST /api/trips/plan
  TourAPI 장소 매칭, 정류장 매칭, 시간표 계산, 위험도 계산을 수행한다.

  현재 시각/위치 기준으로 상태를 재계산한다.

POST /api/trips/{tripId}/recommendations/spare-time
  다음 버스까지 남는 시간 안에 가능한 주변 TourAPI 후보를 추천한다.

POST /api/trips/{tripId}/reschedule
  일정 지연 또는 버스 놓침 상황에서 복구안을 계산한다.

GET /api/admin/data-health
  데이터 import, cache, API fallback 상태를 보여준다.
```

## 18. 심사위원 설득 포인트

1. TourAPI를 핵심 기능에 직접 사용한다.
2. 제주 뚜벅이 여행자의 실제 실패 지점을 겨냥한다.
3. 지도 앱/관광 추천 앱과 역할이 다르다.
4. OpenAI를 사실 생성기가 아니라 검증 가능한 설명 레이어로 제한한다.
5. 구현 불확실한 실시간 도착 기능은 MVP에서 제외해 완성도를 높인다.
6. 데이터 상태와 정확도 한계를 UI에 표시해 신뢰성을 확보한다.

## 19. 최종 제안 문장

타이밍제주는 제주 뚜벅이 여행자를 위한 AI 기반 일정 운영 서비스입니다. 사용자가 자연어로 여행 일정을 입력하면 TourAPI 관광정보와 제주 버스 정류소·노선·시간표 데이터를 결합해 관광지별 출발 권장 시각, 버스 대기 위험, 버스를 놓쳤을 때 주변 추천, 일정 지연 시 복구안을 제공합니다. OpenAI API는 자연어 일정 분석과 설명 가능한 복구안 생성을 담당하고, 버스 시간과 경로 판단은 서버의 TransitEngine이 담당합니다. 이를 통해 렌터카 없이도 제주 여행을 더 예측 가능하고 실패 가능성이 낮은 경험으로 만드는 것이 목표입니다.
